# FabulA: working notes (not in the repo docs)

Project: FabulA, an asynchronous RPG run by a Gemini AI Master, played through MCP.
Repos: jvpreck/FabulA (engine, public) and jvpreck/rpg_adventures (adventures and seeds, private).
Read first: README.md, TOP_LEVEL_REQUIREMENTS.md, gm/protocol.md, gm/state_and_messages.md.

This repository is public: never write secrets, keys or private game data in it.

## Infrastructure
- Vercel project "fabula", production https://fabula-rpg.vercel.app, deploys from main on push. Hobby plan: runtime logs are kept for 1 hour only. Find the project and team ids with the Vercel tools (list_teams, list_projects).
- Supabase project for FabulA (find it with list_projects). Tables gm_* (id, data jsonb, version, index columns). gm_games.turn_closes and gm_submit_actions.turn are real columns.
- Cloudflare Worker "ai-master-turn" runs every 5 minutes and calls /internal/resolve_turn. Its secrets SERVER_URL and CRON_SECRET are set in the Worker. CRON_SECRET was rotated on 2026-11-08 and its value lives in the Vercel env.
- Vercel env: MCP_API_KEY (the connector key), CRON_SECRET, ADMIN_SECRET, GEMINI_API_KEY, SUPABASE_*, GITHUB_TOKEN, CLOUDFLARE_*.
- Saves: Workspace.commit writes all records of a request through the Postgres function gm_commit (supabase/schema.sql, installed in Supabase 2026-11-08, tested in a rolled-back transaction). Without the function the server falls back to one-by-one saves. Re-run schema.sql after schema changes.
- Every AI Master call is counted per day by level, tier, mode, request kind and game in gm_usage (record stats:<day>); the host command gm_usage shows it.
- submit_action accepts request_id: the same id runs once and returns the first answer (kept in the player record, 5 per player, 1 hour).
- Structured output (server/schema.py, GEMINI_STRUCTURED_OUTPUT) is OFF by default. The 2026-11-08 incident (objects declared without fields come back empty) is fixed in the schema: every object has properties or additionalProperties, the schema sent depends on the request (for_request: a character check requires a verdict, an action its parse), tests/test_priority1.py walks it for bare objects, and the live scenarios check that the fields arrive (scenario_checks.contract_problems). With it on the four live scenarios pass, but answers are 5 to 20 times shorter (thinner facts), so TLR-03-015 stays pending and the setting stays off. The provider refuses a schema that is too large with a bare 400 (keep it small: declare only the keys that matter). Free tier limits seen: 250,000 input tokens per minute per model, so about four 55,000-token calls a minute.
- Gemini models: ordered lists per tier, GEMINI_STRONG_MODELS (default gemini-3.6-flash, gemini-3.5-flash, gemini-3.8-flash) and GEMINI_LIGHT_MODELS (default gemini-3.5-flash-lite, gemini-3.1-flash-lite, gemini-3.6-flash). The first that answers is used; a model that times out, answers 5xx or is over quota is skipped for STRONG_BREAKER_SECONDS (900) or LIGHT_BREAKER_SECONDS (120) by every instance (note in gm_usage) and the next answers; a model with another behind it gets one quick retry and a 45 s timeout. Character checks use the light list (CHARACTER_CHECK_TIER=turn sends them to the strong list). The owner asked on 2026-11-09 for the order to follow a live probe of the free tier (tools/probe_models.py, results in README "Gemini models on the free tier"): 3.8 and 3.7 flash answer 503 or time out, 4-argon and 3.1-pro have a free limit of 0, 2.5 models and 3.1-pro-preview on v1 are 404, gemma allows 16,000 tokens a minute; 3.5-flash and 3.6-flash each have 20 requests a day (3.5 also 5 a minute): my own probing used both up on 2026-11-09, so a strong turn close the same day fell to the light list. Implicit caching works on the four usable models (about 50,000 of 52,500 prompt tokens on a repeat), explicit caching is refused for all (limit 0). The earlier decision to keep 3.8 first is superseded by the probe; put it back first with GEMINI_STRONG_MODELS when it recovers.
- Model limits: config.MODEL_LIMITS holds each model's rpm, tpm and rpd (copied by hand from the AI Studio Rate limit page; the owner will not set up Google Cloud, which needs a payment method). Usage.model_headroom counts this server's own calls per model (gm_usage docs model:<model>:<day>), _answer tries models with room first (MODEL_LIMIT_MARGIN 90%) and the rest as a last resort; a 429 naming PerDay leaves the model alone until midnight Pacific, PerMinute for the retryDelay. Update MODEL_LIMITS when the page changes.
- Compact request (TLR-03-014): Engine._dumps sends the envelope without spaces and without empty values (null, "", [], {}) except request, dice and mode (ENVELOPE_COMPACT, default on; the state contract says a missing field is not set); Engine._dice sends DICE_SMALL (6/3/3) for requests that never roll (free_query, message, setup kinds) and DICE_ACTION (40/20/20) otherwise, doubled on a needs_dice retry; the turn close is unchanged. Drop -Pending from 03-014 once deployed.
- Token controls (all switchable): PROMPT_SLIM (sections by request profile turn/play/setup, tags in gm/*.md and rulesets, see gm/README.md), ENVELOPE_RELEVANT (a character's request sees only its slice of the world), GEMINI_CONTEXT_CACHE (explicit caching through v1beta; the free tier refuses it with limit=0 for every model, so it does nothing until the project is on a paid tier; a refusal is remembered per model for an hour in gm_usage). Implicit caching works without it.

## Conventions
- Tests: pip install -r requirements.txt pytest; PYTHONPATH=<deps>:. python3 -m pytest tests -q (161 pass, 4 live skipped). Windows needs tzdata (now in requirements.txt).
- Before releasing a change to gm/, a ruleset or the AI Master's call path, run the live scenarios against Gemini: FABULA_LIVE_SCENARIOS=1 (GEMINI_API_KEY from the environment) pytest tests/test_scenarios.py -k "live and not turn_close" -s (recorded scenarios: tests/scenarios/scenarios.json, checks in tests/scenario_checks.py). turn_close uses the strong model and its daily quota. A live pass is not enough when the checks are lenient: check that the fields that matter arrive (the schema incident of 2026-11-08 passed them).
- Windows terminal: PowerShell scripts are blocked by policy and the Claude app's terminals take their environment when the app starts. The owner's Gemini key is the Windows user variable GEMINI_API_KEY (never put it in a command or a file).
- "tick" was renamed to "turn" everywhere on 2026-11-08, including data keys and DB columns. Never reintroduce "tick".
- Requirement IDs: TLR-xx-yyy (xx chapter, yyy sequence). Unbuilt ones carry "-Pending", dropped only when deployed. 34 are pending on 2026-11-08: the four-level request model, name knowledge and short NPC descriptions, 03-011 (caching, no effect on the free tier), 03-013, 03-014, 03-015 (schema), 07-006 to 07-008, security and operations (02-006 to 02-008, 08-007 to 08-012).
- Implementation order agreed with the owner: Priority 1 (08-006, 06-009, 06-010, 03-016 deployed; 03-015 was deployed in PR 1 and turned back to pending by the hotfix, PR 3). Priority 2 is deployed (PR 4: 05-007, 03-010, 03-012; 03-011 deployed but inert on the free tier). Next: 03-015 (the full schema), 03-014, 07-006, 07-007, then the request-level model (01-009 first), gameplay integrity (06-005 to 06-008, 05-005, 05-006), security and operations, long-term scaling. 08-005 stays pending until level 2 answers are logged.
- Commits end with the Co-Authored-By and Claude-Session lines given by the session.
- For data changes, use SQL migrations and verify with queries. Stored JSON keys follow the code names.
